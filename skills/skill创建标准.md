# 经验Skill生命周期管理器

管理将隐性工作经验转化为结构化、可复用Skill的全过程，涵盖创建、维护与迭代。

## 工作流程

根据用户意图，进入以下对应流程：

### 流程A：创建新Skill

当用户希望将**一项全新的工作或能力**固化为Skill时。

**阶段1：知识提取**
通过提问挖掘用户的显性与隐性知识：
- **核心流程**：标准步骤、可选路径、选择依据。
- **决策逻辑**：关键判断点、条件规则（“如果A则用B”）、例外处理。
- **陷阱与边界**：常见错误、适用场景、不适用场景、特殊变体。

**阶段2：结构设计**
规划Skill的构成部分（在**单文件内组织**）：
1.  **核心逻辑（必须）**：将流程、决策树、判断规则直接写入 `SKILL.md` 正文。
2.  **外部引用（可选）**：
    - **脚本/工具**：在正文中提供脚本的**完整代码或获取命令**。
    - **参考资料**：在正文中提供参考文档的**核心摘要和完整路径**。
    - **模板/资产**：在正文中提供模板的**代码块或文件路径**。

**阶段3：编写与验证**
按以下结构编写单个Skill文件（即本文件本身），并请用户验证：
1.  **YAML元数据**：确保 `name` 和 `description` 准确触发。
2.  **快速开始**：提供最常用场景的一键式指令。
3.  **详细指南**：包含完整流程、决策规则、边界条件。
4.  **资源引用**：列出所有外部脚本、文档、模板及其使用方式。
5.  **迭代记录**：预留区域记录后续修改（见流程C）。

### 流程B：使用与触发Skill

当用户请求执行一项**已由某个Skill定义**的任务时。
1.  根据用户请求，匹配最相关的Skill。
2.  严格遵循该Skill中定义的流程、规则和资源进行操作。
3.  将执行中遇到的问题、新发现的变体记录下来，为迭代（流程C）做准备。

### 流程C：维护与迭代Skill

当用户提出**优化、更新或修复**现有Skill的需求时。
1.  **定位**：读取目标Skill文件（通常位于 `skills/` 目录）。
2.  **分析**：
    - **问题**：是流程错误、边界遗漏，还是资源失效？
    - **更新**：是外部API变了、业务逻辑变了，还是发现了更优路径？
3.  **修改**：更新Skill文件的相应部分。
    - **直接修改正文**：更新流程、规则、判断条件。
    - **更新资源引用**：更改代码块、文件路径或摘要内容。
    - **添加迭代记录**：在文件末尾添加 `## 变更历史` 区域，简要说明每次修改的原因和内容。
4.  **确认**：向用户确认修改已完成。

## 关键原则

1.  **单文件优先**：所有核心逻辑、决策树、资源引用说明应整合在一个 `.md` 文件中。仅当外部资源（如大型脚本、复杂模板）无法内联时，才在文件中提供明确的存放路径和获取指令。
2.  **可读性高于一切**：正文应清晰、具体，避免模糊用语。使用步骤、表格、代码块使逻辑一目了然。
3.  **内嵌判断**：Skill的价值在于封装“判断”。必须明确写出在什么条件下选择什么路径。
4.  **版本意识**：每次重要修改都应在文件中留下记录，形成简易的变更日志。

## 输出质量标准

- **具体可执行**：步骤明确，可直接按顺序操作。
- **判断清晰**：明确“何时做”、“为何这样选”。
- **边界明确**：清晰定义适用与不适用场景。
- **自包含**：作为单文件，应能让读者在不依赖其他Skill上下文的情况下理解并使用。
- **可维护**：结构清晰，便于定位和修改特定部分。
